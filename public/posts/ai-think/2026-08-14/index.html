核心发现极具启发性：

  • 成本差异巨大：Claude Opus 5 一次运行最多消耗 1,055 积分，而 GLM 5.2 平均仅需 27 积分，差距近 40 倍。

🔏 AI 文本水印：技术上注定失败的监管博弈 链接到标题

Sean Goedecke 撰写的《Text AI watermarks will always be trivial to remove》获得了 85 分，这篇深度技术分析几乎戳穿了所有 AI 文本水印方案的泡沫。

他分析了当前主流的两种水印方案：

  1. Google 的 SynthID：通过影响 token 采样过程中的"评分"机制来嵌入可检测特征。问题在于温度为零的推理（确定性输出）无法嵌入水印，且通过另一个 LLM 改写即可轻松移除。

  2. Unicode 同形字水印（疑似被 OpenAI 和 Anthropic 使用）：通过替换普通空格为特殊 Unicode 空格（如 U+2004 或 U+3000）来编码信息。Crazy 的是，Claude Code 之前确实用这招标记过中国用户的请求（虽然此后撤回了）。移除方法更是简单到荒谬——把同形字替换回标准字符即可。

“文本水印将始终容易被移除。这与图像和视频水印不同，文本是一种高度压缩的媒介——你无法在人类不会注意的情况下改动句子的任何部分。”

更关键的是，EU AI Act 要求"水印技术必须可互操作”，这意味着 AI 提供商必须公布他们的水印方案——这与安全领域"通过隐蔽实现安全"的文本水印哲学彻底矛盾。C2PA 签名不适用于纯文本输出（聊天机器人输出没有"文件"容器）。

思考：AI 水印的困境折射出监管和技术之间的根本张力。监管者希望通过水印让 AI 内容可追溯，但文本的本质决定了它无法像图像/视频一样承载不可移除的隐写信息。2026 年底 EU AI Act 的合规期限将至，预料将会看到大量的"合规但不实用"的方案——真正想移除水印的人总有办法。

🔧 AI Agent 基础设施：记忆、协议与本地部署 链接到标题

在 Agent 应用层面，今天有多项值得关注的进展：

MCP Memory（Show HN, 53 分）：一个基于 Google 的 OKF 和 SQLite FTS5 的快速 Agent 记忆系统。这是一个具体而务实的技术方案——当 Agent 需要在跨会话、跨任务场景下保持记忆时，传统的 RAG 方案过于笨重，而简单的键值存储又缺乏语义搜索能力。MCP Memory 在本地用 SQLite 做全文索引，是一个轻量但实用的折衷方案。

OJCP 开放协议（Show HN, 27 分）：一个面向 Agent 可消费的职位数据的开放协议。当招聘数据被不同的 AI Agent（猎头助手、简历优化工具、工作匹配系统）消费时，缺乏标准化的数据格式会带来巨大摩擦。OJCP 试图解决这个问题——虽然目前热度不高，但这类"Agent 间通信协议"的需求只会越来越大。

思考：从 MCP Memory 到 OJCP 再到 OpenCode，一个清晰的信号是：Agent 生态正在从"单模型、单 Agent"向"多 Agent 协作、标准化基础设施"演进。2026 年下半年的关键问题不再是"Agent 能做什么”，而是"Agent 们如何协作"。
