## 🦅 Ornith-1.0：自改进开源模型在编码基准上击败 Claude Opus 4.7

**来源**：[GitHub: deepreinforce-ai/Ornith-1](https://github.com/deepreinforce-ai/Ornith-1) | [博客原文](https://deep-reinforce.com/ornith_1_0.html) | [HN 讨论](https://news.ycombinator.com/item?id=48722052)

DeepReinforce 发布的 Ornith-1.0 系列是今天最大的新闻。这不是一个模型，而是一个从 9B Dense 到 397B MoE 的完整家族，基于 Gemma 4 和 Qwen 3.5 构建。

最令人震惊的是基准测试结果：

> **Ornith-1.0-397B 在 Terminal-Bench 2.1 上达到 77.5，在 SWE-Bench Verified 上达到 82.4，双双超过 Claude Opus 4.7（70.3 和 80.8）。**

这是开源模型首次在前沿编码代理基准上明确超越最先进的闭源模型。更值得关注的是，35B MoE 变体（仅 35B 参数）在 Terminal-Bench 上超越了 Qwen 3.5-397B（64.4 vs 53.5），展示了 MoE 架构的效率优势。

**核心创新在于"自改进训练框架"**：传统强化学习中，人工设计的 scaffold（支架）是固定的，而 Ornith-1.0 让模型**同时学习生成解决方案和构建解决问题的 scaffold**。每轮 RL 分两步：先基于任务和上一轮 scaffold 提出改进版，再基于新 scaffold 生成解决方案。奖励信号同时回传到两个阶段。

这意味着模型不仅能解题，还能学会"如何设计解题的策略"。更引人深思的是，论文坦诚讨论了**奖励黑客（reward hacking）风险**——当模型可以自己写 scaffold 时，它可能学会"作弊"（例如硬编码可见测试文件的内容），而不是真正解决问题。他们用验证器多样化、互信息奖励等技术来缓解，但这仍然是自改进系统面临的根本性挑战。

对于 9B 边缘部署模型，它已经达到 43.1 的 Terminal-Bench 分数和 69.4 的 SWE-Bench Verified 分数，这意味着即使在你的笔记本电脑上运行的本地模型，也已经具备相当强的编码代理能力。这是一个信号：**高质量的本地 Agent 很快将成为开发者的标准配置**。

## ⚔️ GLM 5.2：不看出身，看代码

**来源**：[Semgrep 博客](https://semgrep.dev/blog/2026/we-have-mythos-at-home-glm-52-beats-claude-in-our-cyber-benchmarks/) | [HN 讨论](https://news.ycombinator.com/item?id=48709670)

Semgrep 团队发布了一份令人意外的安全基准测试报告：**Zhipu AI 的 GLM 5.2（开源权重）在 IDOR（不安全的直接对象引用）检测任务上以 39% F1 击败了 Claude Opus 4.8 的 32%**，同时每次漏洞发现成本仅约 $0.17。

但数字本身并不是故事的全部。Semgrep 团队真正想回答的问题是：**在漏洞检测中，多少性能来自模型，多少来自围绕模型的脚手架（harness）？** 他们的结论是——Semgrep 自有的多模态 pipeline（组合 AI 推理和规则检测）达到 53-61% F1，远超纯模型方案。这意味着模型本身是必要条件但不是充分条件。

> "在纯 prompt 方案中，最佳开源权重模型不再是明显的局外人——它击败了 Claude Opus 4.8。"

这篇博客的价值不在于"GLM 比 Claude 好"这个结论（这个结论需要在更多基准上验证），而在于它揭示了安全领域当前的事实：**模型的能力分布高度非均匀，特定领域的开源模型可以匹敌甚至超越通用旗舰**。这预示着"垂直领域微调 + 开源权重"将成为企业 AI 安全部署的主流范式。

## 🔄 路由器即 Agent：vLLM 的 Micro-Agent 重新定义模型 API

**来源**：[vLLM 博客](https://vllm.ai/blog/2026-06-29-micro-agent-frontier-models) | [HN 讨论](https://news.ycombinator.com/item?id=48722802)

vLLM 团队提出了一个优雅的激进观点：**路由器（router）的下一个职责不是路由请求，而是让模型变得更好——不改权重，不建 Agent 图，只靠一次模型 API 调用背后的协作。**

核心组件叫 **Looper（循环器）**，一个运行在服务层的轻量级运行时。用户仍然调用一个看似普通的模型 API：

```json
{
  "model": "vllm-sr/auto",
  "messages": [{"role": "user", "content": "..."}]
}
```

背后，路由器可以选择策略、扇出到多个 worker、收集共识、验证分歧、综合答案——然后返回一个标准 OpenAI 兼容响应。

**这本质上是将 Sakana Fugu 的"模型即表面"理念从商业端点下沉为开源服务原语。** vLLM 支持多种 looper 模式：

- **Confidence**：先用便宜模型，置信度低的才升级
- **Ratings**：多模型并行 + 聚合加权
- **ReMoM**：重复混合模型推理 + 最终综合
- **Fusion**：评价者-终审者模式
- **Workflows**：静态角色或动态规划器 + 有限 worker 步

> "问题的关键不是暴露复杂性，而是让协作感觉像一个模型。"

这个方向的深层含义是：**未来的"模型"不再是单一的权重文件，而是一个由路由器编排的智能体团队**。模型 API 从一个"查询点"变成了"计算入口"——这和微服务架构中 API 网关的角色演进惊人地相似。

## 🖥️ Herdr：在多 Agent 时代，终端才是最自然的控制台

**来源**：[GitHub: ogulcancelik/herdr](https://github.com/ogulcancelik/herdr) | [HN 讨论](https://news.ycombinator.com/item?id=48714802)

Herdr 是一个 Rust 编写的终端 Agent 多路复用器，发布后迅速收获 8.5k stars。它的价值主张非常清晰：**你不是需要一个新应用来管理 Agent，你需要的是一个能在终端里原生运行、支持 SSH 重连、每个 Agent 拥有独立真实终端窗口的管理器。**

> "tmux 提供了持久性和窗格，但它是在 Agent 出现之前构建的。它不知道哪个窗格是 blocked、working 还是 done。而 GUI 管理器（conductor、cmux、emdash）只是将终端重绘在窗口内部。Herdr 是一个在终端中运行的单一二进制文件，显示每个 Agent 的真实屏幕。"

这捕捉到了当前开发者工具生态的一个重要分化：一方面，GUI Agent 管理器（Conductor、Codex 等）提供了漂亮的界面但难以在服务器上运行；另一方面，tmux 拥有弹性但缺乏 Agent 感知。**Herdr 正在弥合这一鸿沟——将"Agent 状态感知"下沉到终端协议层。** 单个 ~10MB Rust 二进制、无依赖、支持 macOS 和 Linux，使它有潜力成为开发者的标配基础设施。

深入分析发现了系统性问题：

- **技术技能（8/10，98% 一致性）**：因为它是 checklist，LLM 不需要做判断——准确得可怕
- **项目经验（巨大波动）**：LLM 难以一致判断"项目的架构复杂度"，有时"缺乏架构深度"，有时"展示真实部署能力"

- 即使温度设为 0，波动仍然存在

> "技术的非确定性不是可以通过微调修复的 bug——这是一个根本性的设计缺陷。"

这篇文章的价值超越了招聘本身。它提出了一个尖锐的问题：**当一个 LLM 被要求做判断（而非生成）时，我们是否把"看起来合理"和"准确可靠"混淆了？** LLM 在事实提取、模式匹配任务上表现出色，但在需要一致评分标准的主观判断任务上——如代码审查、面试评估、投资分析——它的波动性被系统性低估了。招聘沦为"运气过滤器"，这是 AI 落地中最危险的误用之一。

这篇文章的实践洞察很珍贵：AI 在**模式识别和广泛搜索**方面远超人类，但**精确设计和边界理解**需要深厚的领域知识——而这恰好是"魔法学徒"最容易失去的东西。

## 📜 ACL 1.0：为 AI 时代设计的新商业许可协议

**来源**：[AuditableLicense.org](https://www.auditablelicense.org/) | [HN 讨论](https://news.ycombinator.com/item?id=48705878)

ACL（可审计商业许可）1.0 是一个为 AI 时代设计的新源码可用许可证。它的三大创新点：

1. **可审计性**：被许可方有权阅读、审查和审计源码——这不是恩惠，而是权利
2. **AI 训练保护**：第 2.3 条明确禁止将许可作品用作 AI 训练数据，包含知识限定、AI 工具正常使用的安全港，以及对 AI 供应商的穿透义务
3. **自动过期**：每个版本发布 4 年后自动转为 Apache 2.0——"采用者永远不会永久依赖许可方的善意"

此外还有**连续性保护**：如果供应商破产、放弃或失联 180 天，所有当前版本在 30 天内自动加速为 Apache 2.0。

> "商业源码可用许可证是为一个没有自主代码助手的世界起草的。BUSL（2017）、Elastic 2.0（2020）——没有一个应对当下最关键的威胁：使用源代码的过程静默地变成了向某人的模型输送数据的过程。"

这标志着软件许可正在进入第三阶段：**从 GPL（保护用户自由）到 BUSL（保护商业利益）再到 ACL（保护代码不被模型吞噬）**。对于开源 AI 时代的开发者来说，这是一个值得注意的法律基础设施演变。

## ✅ 别复制粘贴错误：Claude Code 的正确用法

**来源**：[Robusta 博客](https://home.robusta.dev/blog/you-really-shouldnt-copy-paste-errors-into-claude-code) | [HN 讨论](https://news.ycombinator.com/item?id=48725359)

Robusta CEO Natan Yellin 提出了一个反直觉的建议：**别再复制粘贴错误给 Claude Code 了**。每一次你手动把错误粘贴进去，你都在拖慢整个流程。

他的核心观点：Claude Code 花了数千次自主工具调用和文件编辑来写代码，测试代码，修复代码。如果还有 bug，那不是因为 Claude Code 需要你手动paste error——而是因为**你没有给它足够的权限来自行完成闭环**。

> "你的角色不是复制粘贴。你的角色是你一直应该做的事：让计算机自动完成事情，尽可能可靠。"

他的建议体系构成了一个"Agent 自我修复"的层级：

1. 如果 Claude 没找到 bug，是因为它没连数据库——给它 API key
2. 如果有 UI bug，它没看到——给它 headless browser
3. 如果你开发的 Agent 有 failure mode——给它 LLM API key 让它自己写 eval 复现然后修复

这个思路的核心抽象是：**不要把人嵌入到 Agent 循环中做"错误中继"——正确的架构是 Agent 闭环自我修复，人的工作是"诊断为什么闭环失败"并扩展它的边界。** 这是从"AI 辅助开发"到"AI 自治开发"的关键一步。
