## 「我不再知道自己擅长什么」—— 软件工程的身份危机

> "I spent 10 years getting good at things that are becoming less and less valuable."
> — human-in-the-loop.bearblog.dev

一篇坦率到令人不安的博文引爆了 HN 社区。作者是一位资深的软件工程师，他描述自己职业生涯中赖以生存的三根支柱正在依次崩塌：

1. **领域知识**——公司招人不再标注"Software Engineer - Area"，而只是"Software Engineer"。
2. **代码实现**——LLM 能在几分钟内完成他需要数天的分布式系统代码。
3. **品位与判断**——当生成式代码泛滥，"好品位"的溢价在雇主的成本计算中越来越难以证明。

HN 社区的反应是撕裂的。一部分人认为这是杞人忧天——"LLM 在我们业务的具体税务法和会计流程上总是搞错"（torben-friis），另一部分人则看到了更深的恐惧："如果模型正在以 rapid rate 提升，那么'现在还不能做 X'只是时间问题"（george_max）。

但最值得深思的或许是 alexpotato 分享的实践经验：他们公司的 LLM 使用经历了四个阶段——从"让 AI 做很多"到"多 agent"，最终回归"单 agent + 构建确定性工具"。结论是：**确定性工具（deployments + testing）提供了二元答案，这是人和 LLM 都能理解的通用接口。** 这暗示着，未来的软件工程可能不是人类 vs AI 的较量，而是**人类设计确定性边界、AI 在边界内执行**的新协作范式。

## 开源蛋白质世界模型：Biohub 的 ESMFold2 超越 AlphaFold

Biohub（Chan Zuckerberg Initiative 旗下的生物医学研究组织）今天发布了蛋白质生物学的"世界模型"——三个开源组件组成的生态系统：**ESMC**（基础语言模型，训练于 28 亿条蛋白质序列）、**ESMFold2**（结构预测模型）、**ESM Atlas**（覆盖 68 亿序列和 11 亿预测结构的可导航地图）。

核心突破在于：**ESMFold2 在抗体-抗原复合物结构预测上超越了 AlphaFold 3**，并能从头设计出具有治疗级别亲和力的蛋白质结合剂。Biohub 针对五个癌症和免疫学靶点（EGFR、PDGFRβ、PD-L1、CTLA-4、CD45）设计的结合剂，在实验室中验证了 36-88% 的 hit rate。对于 PD-L1，设计的结合剂在实验室测试中恢复了 T 细胞信号传导。

> "We've shown that these models have learned such a high-fidelity world model of biology that you can design protein interfaces computationally, take them into the laboratory, and they function as predicted."
> — Alex Rives, Head of Science, Biohub

这意味着**计算蛋白质设计的"预测-验证"周期从数年缩短到数天**。ESM 的核心假设是：在数十亿年的进化序列上训练语言模型，会让它内化蛋白质折叠、相互作用和功能的物理规则。这个假设已经被实验验证——模型在**无人工标注的情况下**学会了蛋白质的"语法"。

值得注意的是，Biohub 选择完全开源这一技术栈。这延续了 CZI 的开源科学传统，但也引发了一个现实问题：当蛋白质设计变得像写代码一样可及，谁将控制"生物学的编译器"？

## 矩阵中的算术：当 LLM 没有手指，它如何做数学？

这是一篇深度机械可解释性文章，拆解了 LLM（具体是 Llama 模型）执行算术运算的内部机制。作者以"算术的编译器"为隐喻，探索了以下几个关键发现：

1. **螺旋编码（Helix）**：模型用类似傅里叶变换的方式编码数字——相位表示循环位置，沿螺旋的位置表示数量级。这不是人类的方式，而是"矩阵的身体"的自创方案。

2. **读取出操作数和运算**：通过小的探针（probe），可以从模型的残差流（residual stream）中恢复出"正在做 gcd"、"操作数 A 是 84"等信息——**即使这些信息从未以文本形式出现在输入中**。

3. **可读 ≠ 可写**：一个关键的教训是——能够从隐藏状态中"读出"一个变量，并不意味着能够"写入"它。实验尝试将正确的计算结果写回模型的残差流，但这比简单的 next-token 纠正要困难得多。"机械可解释性经常庆祝读取；工程想要写入。这是不同的问题。"

> "A readable variable is not necessarily a writable register. Mechanistic interpretability often celebrates reading; engineering wants writing. Those are different problems."

4. **控制实验的设计**：文章严格区分了五种"得到正确答案"的方式——从提示解析到工具调用到激活值推导——并指出许多 interpretability 论文夸大了发现的因果性。

这是 AI 社区稀缺的诚实研究：它报告了原初梦想（在残差流中做 JIT 编译器式的算术替换）未能实现的事实，同时精确地指出了在哪个层次上实验确实成功了。对于研究者和工程实践者来说，区**分"模型确实在计算"和"模型在模式匹配"** 的方法论本身就是一笔财富。

## Tokenomics：Agent 软件工程的"燃料经济学"

一篇来自 arXiv 的论文试图量化 agentic 软件工程中的 token 消耗模式，并提出了**"输入 tokens 占总消耗的 53.9%"** 的核心发现。这颠覆了普遍认知——人们通常认为输出（生成代码）是成本大头，但实际上**agent 在阅读大量上下文上的开销远超输出**。

HN 用户 bob1029 报告其实际使用中看到了约 10:1 的输入输出比，"agent 经常读 100 万 tokens 只为了修补一行代码。" sedatk 则指出了另一个残酷的现实："一个月 GitHub Copilot 完全可用，下个月因为定价调整，我两天就用完了 tokens。定价变动如此剧烈，说明 AI 业务正在快速烧钱。"

这引出了一个被忽视但关键的问题：**LLM 驱动的软件工程的经济可持续性。** 如果输入端的 token 消耗以 10:1 的比例远大于输出端，那么现有的按 token 计费模型可能在 agent 工作流中很快变得不经济。像 Claude Code 的按使用量计划或 GitHub Copilot 的包月制之间的博弈，本质上是在赌 agent 的效率提升能否覆盖 token 成本。
